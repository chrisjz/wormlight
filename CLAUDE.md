# Wormlight — working notes for AI assistants

A living _C. elegans_ in the browser: the Cook et al. 2019 connectome, simulated on the GPU, drives a physically simulated worm. Read `WORMLIGHT_SPEC.md` (the contract) and `PLAN.md` (the design) before changing the simulation.

## Commands

- `npm run dev` — Vite dev server. `npm run build` — typecheck + bundle.
- `npm test` — unit tests (Vitest).
- `npm run lint` / `npm run format:check` — both are CI gates; a pre-commit hook formats staged files.
- `npm run data:build` — rebuilds `public/data/wormlight.v1.json`, its `NOTICE.md`, `DATA_SOURCES.md` and `data/reports/` from the pins in `data/sources.json`. `npm run data:check` is the CI gate that fails when a committed output is stale.
- `npm run docs:fidelity` — regenerates `FIDELITY.md` from the registry and the runtime data; `npm run docs:check` is its CI gate. `npm run docs:screenshot` takes the README's picture, `docs/images/app.png`, from the built app in headless Chrome on this machine's GPU (build first); no gate checks it, so take it again when the app's look changes.
- `npm run visual:capture` then `npm run visual:compare` — capture the fixed views from `dist/` in headless Chrome and compare them with `tests/visual/baseline/` (build first). Baselines come from CI's captures on SwiftShader, Chrome's software GPU, not a local GPU: take the `visual` artifact of a run on a branch of this repository (never a fork's), at the commit being baselined, and copy only its `<view>.png` files. A new view has no baseline on its first CI run, which fails its comparison for that reason alone: check its log says so, then take that run's artifact. `VISUAL_NEW_BASELINES=1` lets a local comparison pass without one. CI pins Chrome to the version puppeteer-core targets; bump both together and refresh the baselines in the same PR.
- `npm run gpu:parity` — checks the GPU against the CPU reference in headless Chrome (PLAN §7.2), the brain, the whole loop and the odour field's stepping, through `parity.html`, which the dev server serves and the build leaves out; `npm run dev` then `/parity.html` shows the same checks in any browser. `npm run gpu:parity:safari` runs them in Safari on the Mac's GPU through safaridriver (`scripts/safari.ts`), which is the parity part of the Safari check (`npm run app:safari` is the app's); it needs Safari's Developer setting "Allow remote automation", and runs locally only. CI runs it on SwiftShader, its one-second checks dealt across four Chrome processes, since SwiftShader runs a world on one core (`--shards=N`, default 4 on CI and 1 elsewhere; a sharded run takes no benchmark). `-- --long` (or `/parity.html?long`) adds long-run parity, about 8 minutes in Chrome on an M5 Max on track S's fit, short checks included, 11 to 18 on earlier fits and in Safari, and too long for CI; since checkpoint 1 is partial it compares each run's crawl as checkpoint 1 measures it (`src/validation/longRuns.ts`).
- `npm run harness -- --checkpoint <n>` — runs checkpoint 0 (the silenced network: crawling, touch and hour-long chemotaxis runs, about 3.5 min on 14 workers, with checkpoint 1, on the refit and on track S's fit, a sham twin forked at each touch; `--jobs N` sets the workers), checkpoint 1 (seconds), or checkpoints 2 and 3 (the touch reflexes, sharing one set of trials: from seed 1 upwards, each worm touched once during forward crawling and forked into front, back and sham copies, about 20 s on 14 workers) on the CPU reference, one worker per core, and regenerates that checkpoint's section of `VALIDATION.md` between its markers. Commit the code first, so the page records a clean commit: changes to Markdown alone don't count against it, but untracked files do. `--trials` and `--seconds` shorten a run for a look, the assay's worms included, and leave `VALIDATION.md` alone. `-- --sensitivity` runs the sensitivity settings instead (spec §2.4; PLAN §2.4, §3.2): checkpoint 1's trials and the silenced network's under sixteen settings, of the uncertain signs, the scales and track S's rest offsets, its offsets off and AVA's added, reported and not graded, into their own section (about 3.5 minutes on 14 workers). The offset settings refuse a fit that doesn't run S's offsets.
- `npm run calibrate` — PLAN §7.3's calibration of track R's model in R's second round: stage 1, CMA-ES with restarts over its twelve calibrated parameters on the kinematics alone, from their provisional values; then stage 2, σ_n and τ_n alone on all four targets, the rest held. Each candidate is scored on 4 trials on the CPU reference, one worker per core, then each stage's ten best are re-run on fresh seeds (about an hour on 18 cores). `-- --probe` first runs stage 1 four times at 400 evaluations and grades each pick on seeds 2001–2020, writing `data/calibration/r3-probe.json`: the full run goes ahead only if one grades at least partial (about 45 minutes; `--resume` keeps the runs already graded). Commit the code first: a run records its commit. It rewrites `harness-out/calibration-r3.json` after every generation, and `--resume` takes a stopped run up again. A full run also writes `data/calibration/r3.json`, committed. R's refit, the first round's, is `data/calibration/r2.json`, its first fit `r1.json`, and the planned model's `planned.json`, which `src/science/planned.ts` holds, as `tests/calibration.test.ts` checks. `--budget` shortens stage 1 for a look. `-- --survey` runs the survey of the bounded model (PLAN §9): stage 1 sixteen times at 250 evaluations in the conductance form, from a Latin hypercube's starts, each pick graded on seeds 3001–3020, writing `harness-out/calibration-survey.json` and `data/calibration/survey.json` (2 h 16 min on 14 workers; `--resume` keeps the searches already graded). It ran on 2026-09-29 and found a crawl (DECISIONS.md). `-- --round-3` runs R's third round, its last (PLAN §7.3, §9): phase 1, sixteen searches of 250 in the conductance form from the survey's starts, on the crawl alone with a speed target of 0.15; then phase 2, the four whose final checks score lowest continued to 750 each, their first 250 replayed. It grades nothing, and writes `harness-out/calibration-r5.json` and `data/calibration/r5.json`, its four picks in the order they take §7.2's comparison (3.2 hours on 14 workers when it ran; `--resume` keeps the searches already finished and replays a stopped one's evaluations). It runs once, after a survey that found a crawl, and no mode starts afresh over a stopped run: resume it, or move its file aside. Since checkpoint 1's frequency took its band (2026-10-01), round 2's full run, the probe and the survey also refuse while their committed records exist, since those were made under the plain count. It ran on 2026-09-29, and none of its picks passed §7.2's comparison, so the refit stays and R has ended (DECISIONS.md). `-- --bounded` calibrates the bounded model once by the refit's procedure, writing `data/calibration/r4.json`; it refuses to run, since the survey found a crawl, unless a later rule calls for it. `-- --track-s` runs track S's calibration (PLAN §7.3, §9; DECISIONS.md, 2026-10-01): round 3's procedure on S's model, its measured signs, the D-types' offset and its rectifier, with its own bound on g_p, writing `harness-out/calibration-s1.json` and `data/calibration/s1.json`, which names the frequency band it scores on; it runs once, refusing while `s1.json` exists, and `--resume` takes a stopped run up (about 3 hours on 14 workers, as round 3 took).
- `npm run equivalence -- --fit <refit|round-2|planned|round-3|track-s> [--pick N]` — PLAN §7.2's comparison with the noise on: a fit's 200 trials at 2.5 and 1.25 ms, each step in a copy of the committed tree under `harness-out/equivalence/`, then each clause's percentile interval for the difference against its margin. R's fits take their values from their calibration records (`r2.json`, `r3.json`, and `r5.json` for round 3's picks), whatever the registry holds. Round 3's picks take it in their order, `--pick 1` first: a full run of pick N needs picks 1 to N − 1 to have failed it, and writes `data/equivalence/round-3-pick-N.json`. The first to pass is round 3's fit, and its run also grades checkpoint 1 from the comparison's first 20 trials at dt, adds the speed's interval, and runs those trials again with the head switch off and weakened and with classes lesioned, writing `data/calibration/r5-chosen.json`; none of round 3's picks passed, so it was never written. Track S's picks (`--fit track-s`, from `data/calibration/s1.json`) take it the same way on S's model, writing `data/equivalence/track-s-pick-N.json`, and the first to pass writes `data/calibration/s1-chosen.json`; their records name the frequency band. Commit first. About 3.5 minutes for the refit and 7 for the planned fit on 18 cores. Trees and records sit in folders named by a hash of the sources the trials depend on, so a run at other sources never touches them, and matching records are reused. A full run writes `data/equivalence/<fit>.json` and regenerates `VALIDATION.md`'s section, and refuses while that record exists: the committed ones were made under checkpoint 1's plain count of crossings, and none is regraded under the band that replaced it (DECISIONS.md, 2026-10-01); `--trials` shortens a run for a look and writes only to `harness-out/`.
- `npm run plate:bench` — the app's frame rate and the worm's speed at several speeds, on this machine's GPU (build first): in headless Chrome, or with `-- --window` in a visible Chrome window, or `-- --safari` in Safari through safaridriver; `--view=plate` times a view alone. Headless Chrome paces its own frames; a window shows what a display does, and must stay uncovered. It counts the page's frames itself, and the steps the GPU ran: a speed is held if every second has at least 57 frames and the worm runs within 2% of it.
- `npm run app:safari` — milestone 6's Safari check of the app (build first): the built app driven in Safari through safaridriver, eleven scenarios from the split view to Copy link, each needing no error once the page is ready, the GPU stepping the worm, every view drawn and its own check, with screenshots in `harness-out/safari-app/`. It needs Safari's "Allow remote automation" and its window uncovered, runs locally only, and leaves a link on the clipboard.
- `node scripts/experiments/go-no-go/run.ts` — reruns milestone 0c's go/no-go experiments, whose tables are in `DECISIONS.md` (2026-09-26).
- `node scripts/experiments/convergence/run.ts` — reruns the convergence study, whose tables are in `DECISIONS.md` (2026-09-28): the oscillator alone, both fits at four steps from 2.5 to 0.3125 ms, and the A-types' part in the step dependence. It runs each step in a copy of the committed tree under `harness-out/convergence/`, so commit first; about 12 minutes on 18 cores. It reuses a record set only when its manifest matches the trees its trials depend on.
- `node scripts/experiments/fixes/run.ts` — reruns the second numerics study (DECISIONS.md, 2026-09-28): a coloured noise current and neural sub-steps, judged at seven points with a gain sweep, at loop steps of 2.5 and 1.25 ms. It builds its own step trees under `harness-out/fixes/` with the convergence study's code (`scripts/experiments/trees.ts`), so commit first; about 80 minutes of trials on 18 cores, then about 90 minutes grading on one.
- `node scripts/experiments/rectification/run.ts` — prints track S's rectifier's two reported checks, the amplifier and the input resistances, whose tables are in `DECISIONS.md` (2026-10-02); under a second, and it writes nothing.
- `uv run --project tools/reference python tools/reference/ni_reference.py` (and `cook_reference.py`) — regenerate the port and production check goldens in `tests/fixtures/`. The checks in `tests/` fail when a golden is stale (its script, its pinned inputs or Cook's wiring changed since it was made) or was edited by hand.

## Hard conventions

- **Behaviour must emerge from the connectome.** Only the layers in spec §1.1 may sit outside the network, and nothing outside it may read behavioural state ("reversing", "near food"). Adding a layer is a major deviation: ask the maintainer first.
- **The CPU reference is the scientific ground truth.** WGSL kernels mirror it and behavioural trials run on it. A model change lands in both, with a parity test.
- **A change that moves how the worm behaves raises the model version,** `MODEL_VERSION` in `src/sim/version.ts`, which links carry (PLAN §1). `tests/version.test.ts` fails when its fingerprint of short runs, or the data's version, moves: add an entry to `tests/model-versions.json`, never edit one (CI's `npm run versions:check` compares it with `main`), with a new version unless only the data changed.
- **Every component, parameter and data element carries a fidelity level and a source** in the registry (spec §1.3): `src/science/citations.ts`, `params.ts` and `fidelity.ts`. `FIDELITY.md` is generated from the registry and `DATA_SOURCES.md` from `data/sources.json`; never edit either by hand. A value we set ourselves is level 1 or 0 and counts toward the free-parameter budget in `PLAN.md` §6.2, which a test enforces. Every citation the code, the runtime data or a generated page uses goes in `citations.ts` once, checked against Crossref or the publisher, and is referred to by id; prose in PLAN and DECISIONS, and the records in `docs/`, may cite others. A record in `docs/` is kept as it was made: corrections go in place, each marked with its date, and its status note says so. Editing `citations.ts` changes the runtime file's `meta.citations`, so rerun `npm run data:build` as well as `npm run docs:fidelity`.
- **Neural Interactome's matrices are indexed [post, pre].** Read `Gs.npy` the wrong way round and every port-check neuron fails. The port check drives Neural Interactome's own code for that reason.
- **Validation thresholds are fixed in advance** in `PLAN.md`. Changing one after seeing results is logged in `DECISIONS.md`, and the checkpoint is marked as changed.
- **Never invent citations.** Check every number against its source, and say so when unsure.
- Generated data comes from scripts that read pinned, hashed sources; never hand-edit it, rerun the generator. The scripts in `scripts/` run on Node's built-in TypeScript support, so their relative imports carry the `.ts` extension.
- Docs use British spelling, as the spec does.

## Process

- One focused PR at a time, always based on `main`, with no stacked PRs. The maintainer merges each before the next starts.
- Commit messages: an evocative first line, then a short story of the why. Write multi-line messages with `git commit -F <file>`.
- CI runs `checks` on every change, and `data`, `visual` and `gpu` only when a file they use changes (`scripts/ci/changes.ts`). Their code is traced through the imports of their pages and scripts when CI runs; when a job starts reading a file it doesn't import, such as runtime data, add it to that job's `reads` there.
- Releases (PLAN §8 has the rules for a minor or a patch): a pull request sets `version` with `npm version X.Y.Z --no-git-tag-version`, and the same `version` in `CITATION.cff` with `date-released` the day of the tag, in local time; `tests/release.test.ts` holds them together. After it merges, and only with the maintainer's go-ahead, since both are public: find its merge commit with `gh api repos/chrisjz/wormlight/pulls/<n> --jq .merge_commit_sha`, check `main`'s CI passed on it, `git fetch origin`, `git tag -a vX.Y.Z <sha> -m "Wormlight X.Y.Z"` and `git push origin vX.Y.Z`. Then `gh release create vX.Y.Z --verify-tag --draft --title "Wormlight X.Y.Z" --notes-file <file>`, and once the maintainer has seen the draft, `gh release edit vX.Y.Z --draft=false`. The notes give the model and data versions, the checkpoints' status and what changed since the last release, pointing at `DECISIONS.md`. If the merge slips past `date-released`, a pull request corrects it first, and its merge commit is the one tagged.
- `gh pr edit` has been broken by a GraphQL deprecation; use `gh api -X PATCH repos/chrisjz/wormlight/pulls/<n>` instead.
- Prettier reflows Markdown. A nested ordered list that starts at 0 needs a blank line before it, or it merges into the paragraph above. A line straight after a list item is folded into that item, so leave a blank line before a following paragraph. After any scripted edit, grep-verify the result.
